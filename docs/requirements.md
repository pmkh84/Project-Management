# ProjectHub — Software Requirements Specification

**Version:** 0.1
**Status:** Draft

## 1. هدف سیستم

ساخت یک سیستم تحت وب برای مدیریت تیم‌ها، پروژه‌ها و وظایف که امکان همکاری چند کاربر با نقش‌ها و سطوح دسترسی متفاوت را فراهم کند.

## 2. کاربران سیستم

### Team Admin

مدیر تیم می‌تواند:

- اعضای تیم را مدیریت کند.
- پروژه ایجاد، ویرایش و حذف کند.
- وظایف پروژه‌ها را مدیریت کند.
- وظایف را به اعضای تیم اختصاص دهد.
- پیشرفت پروژه‌ها را مشاهده کند.

### Team Member

عضو تیم می‌تواند:

- پروژه‌هایی را که به آن‌ها دسترسی دارد مشاهده کند.
- وظایف اختصاص‌یافته به خودش را مشاهده کند.
- وضعیت وظایف خودش را تغییر دهد.
- برای وظایف قابل مشاهده نظر ثبت کند.

یک کاربر می‌تواند در یک تیم مدیر و در تیم دیگر عضو عادی باشد.

## 3. نیازمندی‌های عملکردی (Functional Requirements)

### Authentication

**FR-01:** کاربر باید بتواند ثبت‌نام کند.

**FR-02:** کاربر باید بتواند وارد حساب خود شود.

**FR-03:** کاربر باید بتواند از حساب خود خارج شود.

**FR-04:** سیستم باید دسترسی به اطلاعات خصوصی را به کاربران احراز هویت‌شده و مجاز محدود کند.

### Team Management

**FR-05:** کاربر باید بتواند یک تیم ایجاد کند.

**FR-06:** سازنده تیم به‌صورت پیش‌فرض مدیر آن تیم باشد.

**FR-07:** مدیر باید بتواند کاربران ثبت‌نام‌شده را به تیم اضافه کند.

**FR-08:** مدیر باید بتواند اعضای تیم را حذف کند.

**FR-09:** هر کاربر بتواند عضو چند تیم باشد.

### Project Management

**FR-10:** مدیر تیم باید بتواند پروژه ایجاد کند.

**FR-11:** هر پروژه باید به یک تیم تعلق داشته باشد.

**FR-12:** مدیر باید بتواند پروژه را ویرایش یا حذف کند.

**FR-13:** اعضای تیم باید بتوانند پروژه‌های متعلق به تیم خود را مشاهده کنند.

### Task Management

**FR-14:** مدیر تیم باید بتواند برای پروژه‌های تیم وظیفه ایجاد کند.

**FR-15:** هر وظیفه باید دارای عنوان، وضعیت و اولویت باشد.

**FR-16:** توضیحات و مهلت انجام وظیفه اختیاری باشند.

**FR-17:** هر وظیفه بتواند حداکثر به یک عضو تیم اختصاص داده شود.

**FR-18:** وضعیت وظایف یکی از موارد زیر باشد:

- To Do
- In Progress
- Done

**FR-19:** اولویت وظایف یکی از موارد زیر باشد:

- Low
- Medium
- High

**FR-20:** عضو تیم بتواند وضعیت وظایف اختصاص‌یافته به خودش را تغییر دهد.

**FR-21:** مدیر تیم بتواند وظایف پروژه‌های تیم را ویرایش یا حذف کند.

### Comments

**FR-22:** اعضای تیم بتوانند روی وظایف قابل مشاهده نظر ثبت کنند.

**FR-23:** هر نظر باید نویسنده و زمان ثبت مشخص داشته باشد.

### Dashboard

**FR-24:** سیستم باید تعداد کل وظایف هر پروژه را نمایش دهد.

**FR-25:** سیستم باید تعداد وظایف هر وضعیت را نمایش دهد.

**FR-26:** سیستم باید درصد پیشرفت پروژه را بر اساس تعداد وظایف تکمیل‌شده محاسبه کند.

### Activity History

**FR-27:** سیستم باید تغییرات مهم مانند ایجاد وظیفه، تغییر مسئول و تغییر وضعیت را ثبت کند.

## 4. قوانین کسب‌وکار (Business Rules)

**BR-01:** هر پروژه دقیقاً به یک تیم تعلق دارد.

**BR-02:** هر وظیفه دقیقاً به یک پروژه تعلق دارد.

**BR-03:** مسئول وظیفه باید عضو تیم مالک پروژه باشد.

**BR-04:** کاربر نباید به اطلاعات تیمی که عضو آن نیست دسترسی داشته باشد.

**BR-05:** تنها مدیر تیم می‌تواند اعضا و پروژه‌های آن تیم را مدیریت کند.

**BR-06:** کاربر نمی‌تواند با تغییر شناسه‌های ارسالی به API به داده‌های غیرمجاز دسترسی پیدا کند.

**BR-07:** درصد پیشرفت پروژه برابر است با تعداد وظایف Done تقسیم بر تعداد کل وظایف ضرب‌در ۱۰۰. برای پروژه بدون وظیفه، درصد پیشرفت صفر است.

## 5. نیازمندی‌های غیرعملکردی (Non-Functional Requirements)

**NFR-01 — Security:** رمز عبور کاربران نباید به‌صورت متن ساده ذخیره شود.

**NFR-02 — Validation:** ورودی‌های API باید اعتبارسنجی شوند.

**NFR-03 — Maintainability:** منطق برنامه باید ساختار ماژولار و قابل نگهداری داشته باشد.

**NFR-04 — Testing:** قابلیت‌های اصلی و کنترل دسترسی باید تست خودکار داشته باشند.

**NFR-05 — Documentation:** APIها و راه‌اندازی پروژه باید مستند شوند.

**NFR-06 — Reliability:** خطای یک درخواست نباید باعث ذخیره ناقص عملیات وابسته در دیتابیس شود.

## 6. سناریوی اصلی (User Flow)

1. مدیر ثبت‌نام می‌کند.
2. مدیر یک تیم ایجاد می‌کند.
3. مدیر کاربر دیگری را به تیم اضافه می‌کند.
4. مدیر پروژه جدید ایجاد می‌کند.
5. مدیر وظیفه جدید ایجاد می‌کند.
6. مدیر وظیفه را به عضو تیم اختصاص می‌دهد.
7. عضو تیم وارد سیستم می‌شود.
8. عضو، وظیفه خود را مشاهده می‌کند.
9. عضو وضعیت وظیفه را تغییر می‌دهد.
10. مدیر وضعیت جدید را مشاهده می‌کند.

## 7. قابلیت‌های فازهای بعدی

- اعلان تلگرام و ایمیل
- پردازش غیرهم‌زمان با Celery و Redis
- به‌روزرسانی لحظه‌ای با WebSocket
- فیلتر و جست‌وجوی پیشرفته
- گزارش‌های تحلیلی
- استقرار با Docker
- راه‌اندازی CI/CD

## 8. موارد خارج از محدوده نسخه اول

- اپلیکیشن موبایل مستقل
- پرداخت آنلاین
- گفت‌وگوی خصوصی کاربران
- هوش مصنوعی برای مدیریت پروژه
- معماری Microservices

این موارد در MVP پیاده‌سازی نمی‌شوند.

## 9. معیار پذیرش سناریوی اصلی

سناریوی اصلی زمانی پذیرفته می‌شود که:

- مدیر بتواند تیم، پروژه و وظیفه ایجاد کند.
- عضو بتواند وظیفه اختصاص‌یافته را مشاهده کند.
- عضو بتواند وضعیت آن را تغییر دهد.
- مدیر تغییر ایجادشده را مشاهده کند.
- کاربر غیرمجاز نتواند اطلاعات تیم را بخواند یا تغییر دهد.
- تست‌های مرتبط با این سناریو با موفقیت اجرا شوند.
